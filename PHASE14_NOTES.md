# Phase 14 notes — Cross-cutting: security & tenant isolation audit

Companion to [`../Notification_Reports_Integration_Plan.md`](../Notification_Reports_Integration_Plan.md) Phase 14. Backend-only. This phase found and closed real gaps rather than confirming everything was already fine — listed here in the order they were found, not just the ones that turned out clean.

## A real data leak found and fixed

`User.deviceToken` — the deprecated single-token field superseded by the `DeviceToken` collection back in Phase 1 — had no `select: false` on its schema definition, unlike `password` right next to it. Concretely: any endpoint returning a full `User` document (`getSingleUser`, `generalGetAllUsers`) would include a legacy user's stale FCM/APNs token in the response to **whoever was allowed to view that profile** — an admin viewing an employee, a company viewing their own employee. Confirmed the field is genuinely never written to anymore (checked `auth/common.ts`'s login flow directly), so this was pure legacy-read exposure, not an active write path. Fixed with `select: false` (`user.model.ts`), the same pattern `password` already used one line above it — closes the leak at every call site at once rather than needing to patch each query individually. 3 new tests prove it (`user.security.test.ts`), covering an admin viewing another user, an admin listing all users, and a company listing their own employees.

`NotificationPreference` was checked the same way and found clean — it's a fully separate collection with no `populate`/virtual reference from `User`, so there's no equivalent leak path for it.

## A route-level auth bug, closing the loop from Phase 12

Not new to this phase, but worth restating here since Phase 14 exists to catch exactly this class of thing: Phase 12 found `notifications.route.ts` silently 403ing `COMPANY`/`SUPER_ADMIN` out of every notification endpoint, breaking Phase 7 and Phase 9's already-shipped work. This phase's own audit of the *other* newly-added routes (device tokens, report endpoints, async job status) found the equivalent role wiring correct everywhere else — but also found a **coverage** gap of the same shape: Phase 8 added ADMIN/SUPER_ADMIN support for the async report-job endpoint and tested it thoroughly at the service level (`reportjob.service.test.ts`), but no test ever exercised the actual HTTP route with those roles — meaning a route-level auth regression (like Phase 12's) could have slipped through even here without being caught. Closed with two new route-level tests (`timetracker.reports.route.test.ts`): an ADMIN creating a job and a SUPER_ADMIN listing jobs, both through the real Express route, not the service function directly.

The same audit turned up a second, completely untested tenant boundary: `GET /timetracker/reports/monthly` has had a company-ownership check since Phase 0 (`generateMonthlyPdfReport`'s `User.findOne({_id, company})` guard), but — confirmed by grepping the whole repo — no test anywhere had ever exercised it. The parallel attendance-report route already had this exact test; the monthly one didn't. Added three tests: a company rejected for an outside employee (403), a company allowed for their own employee (200), and an EMPLOYEES-role caller always getting their own report regardless of what `employee` id they pass (200, self-substitution confirmed rather than assumed).

## Rate limiting: existed, wired to nothing, now actually protecting the two endpoints the plan named

`rateLimitMiddleware` (`src/app/middleware/rateLimitter.ts`) already existed as a generic, configurable, IP-keyed factory — but a full-repo grep confirmed it was applied to **zero routes**. Wired it into the two the plan specifically calls out:
- `POST /devices/register` — 30/minute per IP (well above any legitimate client's real call frequency: once per login plus occasional token refreshes).
- `GET /notifications` — 60/minute per IP (comfortably covers the web bells' 45s poll interval and mobile's on-demand fetches, even several users behind one NAT).

Placed before `auth()` in both route chains so a flood of invalid-token requests is rejected at the cheap layer first. Wiring it up surfaced a real, separate bug: the middleware's `return res.status(429).json(...)` resolved to `Response`, not `void`, which had simply never been type-checked against Express's `RequestHandler` signature before because it had never actually been passed to `app.use`/`router.get` anywhere. Fixed the return type once the mismatch was visible (`tsc --noEmit` now clean).

The middleware itself had **zero test coverage** before this phase too — added 5 unit tests (`rateLimitter.test.ts`, exercised directly against fake req/res/next rather than by firing 30+ real requests at a live route) covering: under-limit requests pass through, over-limit requests get 429 and don't call `next()`, different IPs are tracked independently, the rate-limit headers are set correctly, and the middleware fails open (never blocks traffic) if the underlying cache throws. Also added one assertion each in the real route test files confirming the `X-RateLimit-Limit` header is actually present on a real request through the real route — proof the middleware is wired in, not just that the standalone function works.

**A known limitation, not fixed:** the underlying cache (`CacheService`) is an in-process `NodeCache`, not Redis — its own comment says it's "matching the old behaviour where all instances talked to the same Redis server," implying it used to be Redis-backed and was downgraded to in-memory at some point before this phase. For a single-instance deployment (the only kind this project's `server.ts` currently sets up) this rate limiter is fully effective. If the backend is ever deployed with multiple instances behind a load balancer, each instance gets its own independent counter, and the effective limit becomes `configured limit × instance count` — a real weakness worth knowing about, but re-adding Redis is real infrastructure work well outside a "wire up and test the existing middleware" task, so it's flagged here rather than attempted.

## The manual penetration-style check the plan explicitly asks for

Added directly (`devicetoken.route.test.ts`): a request to `POST /devices/register` with a legitimate auth token but a body containing `userId`/`user`/`authId` fields pointing at a different, real user — confirmed the device is attached to the *authenticated* caller regardless, never the injected value. This was already structurally guaranteed (the controller only ever destructures `{token, platform, appVersion}` from the body), but the plan asks for this to be verified, not just architecturally true — now it's a real, running test instead of an inference from reading the code.

## The deployment guide

`BACKEND_DEPLOYMENT_GUIDE.md`, which the plan's task list references by name, **did not exist anywhere in this repository** before this phase — checked directly (`find . -iname "*deploy*"`), not assumed. `README.md` had an "Environment Variables" section instead, but it was stale template boilerplate that didn't match reality: `MONGODB_URI` instead of the real `DATABASE_URL`, `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_SECRET` instead of the real `CLOUDINARY_NAME`/`CLOUDINARY_SECRET`, AWS S3 and SMTP variables that aren't used anywhere in this codebase at all, and no mention of Firebase, JWT refresh/temp secrets, or the super-admin seed credentials. Created the real guide from `src/config/index.ts` (the actual code that reads these variables, not the aspirational template), with `FIREBASE_SERVICE_ACCOUNT_BASE64` — the one genuinely new secret this whole plan introduced (Phase 2) — called out specifically, including the exact expected format (base64 of the full service account JSON) and a note that its absence degrades gracefully (verified directly: this exact "Failed to initialize Firebase Admin" log line has appeared throughout this environment's own test runs across every backend phase of this plan, and every affected test still passed). Replaced README's stale inline list with a pointer to the new guide rather than maintaining two contradictory sources.

While building the guide, found (but did not fix) a second, inert inconsistency: `.env` defines `TEMP_JWT_EXPIRES_IN`, but `config/index.ts` reads `TEMP_JWT_EXPIRE_IN` — the names don't match. Checked the actual impact before deciding whether this needed fixing: nothing in the codebase reads `config.jwt.temp_jwt_expire_in` at all, so this is a dead mismatch with zero runtime effect, not an active bug — documented in the new guide for whoever eventually cleans up the `tempAuth` code path it belongs to, not fixed here (outside this phase's actual scope, and touching unrelated dead code isn't warranted by anything this audit needs).
