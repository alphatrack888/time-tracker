# Phase 16 notes — QA: edge-case & regression test matrix

Companion to [`../Notification_Reports_Integration_Plan.md`](../Notification_Reports_Integration_Plan.md) Phase 16. Cross-cutting: backend, both React dashboards, and the Flutter mobile app.

This phase exists to catch integration-level gaps that only show up once every earlier phase's work is combined — not to re-run each phase's own exit criteria. As with every phase in this plan, "verified" here means proven by automated test or direct code inspection, never assumed: there is no staging environment, physical device, or reachable live backend anywhere in this working environment, the same gap called out in every earlier phase's own notes.

## Two real bugs found and fixed

**Both dashboards' unread badges undercounted.** `NotificationServices.getNotifications` (`notifications.service.ts`) has computed a server-side, live `countDocuments`-based `meta.unreadCount` since Phase 12 — its own comment even says this was added specifically because "the admin/company dashboards' bells (Phase 7/9) approximated this from just the 20 most recent items and explicitly deferred a real count to this phase." Checking the actual bell components (`NotificationBell.jsx` in both `time-tracking-admin-dashboard` and `time-tracking-company-dashboard`) found that deferred fix was never actually made — both still computed `unreadCount` by filtering the fetched 20-item dropdown page client-side. A user with more than 20 unread notifications would see an undercounted (or badge-invisible-when-nonzero) count. Fixed both to read `data?.data?.meta?.unreadCount`, falling back to the old page-local computation only if a response ever omits it.

**Mobile's notification state went stale after being backgrounded.** `NotificationScreenController` is registered `fenix: true` (`initial_bindings.dart`) — an app-wide singleton whose `onInit()`, and therefore its one `fetchNotifications()` call, only ever runs once near app startup. Its `unreadCount` is read directly by `home_screen.dart`'s badge for the whole app lifetime. The live socket handler (`socketCalling()`) only accounts for notifications that arrive while the socket is actually connected — nothing backgrounds-and-catches-up. So after the app sat backgrounded for any length of time, the badge and list would silently go stale until the user happened to manually pull-to-refresh the notifications screen itself. FCM's own token-refresh handling (`push_notification_service.dart`) was already correct — this was specifically about the notification *list/badge* state, not push delivery. Fixed by mixing `WidgetsBindingObserver` into the controller and calling `fetchNotifications(isRefresh: true)` on `AppLifecycleState.resumed` — the same pattern `HomeScreenController` already uses for its own (timer-state) resume handling, so this isn't a new pattern introduced to the codebase, just applied where it was missing.

See the expanded table in the plan document itself for full detail per row. Summary of what required new work versus what was already correct:

- **Already correct, verified by existing or code-inspection means, no changes needed:** no-devices-registered fan-out, in-app-row-independent-of-push-outcome (covers the "phone off" row as far as this codebase's own responsibility goes — FCM's offline store-and-forward itself is Google's infrastructure, outside this repo's testable surface), and the dashboards' polling mechanism (both bells use RTK Query's own `pollingInterval`, not a hand-rolled `setInterval` — there's no interval-accumulation surface to leak from, by construction of using the library's built-in mechanism rather than reinventing it).
- **N/A, confirmed against the real data model rather than assumed:** "company admin with 2 companies" — `User.company` is a single `ObjectId` ref, never an array, and ADMIN/SUPER_ADMIN carry no `company` value at all (their cross-company access from Phase 8 is a permission, not a membership list).
- **New tests written to lock in already-correct-by-design behavior:** the DST transition row (proving the UTC-everywhere design is immune, not just asserting it from reading the code) and the preferences-opt-out-mid-sweep row (proving the sweep never caches a user's preferences, so there's no stale value to race against).
- **New tests written to lock in a real, previously-undocumented, deterministic rule:** the mid-session report generation row — `totalTime` only advances at pause/stop, so an active never-paused session reports `workMs: 0` the entire time it runs. Not a bug; a defined rule that had no test proving it was actually deterministic rather than accidentally-consistent.
- **New tests written for a scenario with genuinely no prior coverage:** the uninstall/reinstall row (`devicetoken.service.test.ts`) and the load/volume sanity check (`notificationHelper.volume.test.ts`, its own section below).
- **Real bugs found and fixed:** the two described above.

## Load/volume sanity check

`notificationHelper.volume.test.ts`, two tests:
- 500 concurrent recipients, each with their own registered device, fanned out exactly the way a real bulk trigger does it (`Promise.all` over independent `sendNotification` calls, mirroring `project.service.ts`'s employee-added/-removed `dispatchNotification` loop, which is itself fire-and-forget so the triggering HTTP request is never held open waiting on it) — all 500 `Notification` rows created, all 500 push attempts made, completes comfortably inside a 25s bound in this environment's own `mongodb-memory-server` (not a proxy for production infrastructure throughput, just a floor proving this doesn't hang or deadlock).
- One recipient with bad data (an invalid ObjectId) mixed into a burst of 499 good ones — confirmed the bad one fails independently without affecting delivery to any of the other 499.

The other shape of "bulk" — one user with many devices hitting FCM's actual 500-token multicast limit — was already covered before this phase (`pushnotificationHelper.configured.test.ts`, "batches more than 500 tokens into multiple multicast calls"); this phase's addition is specifically the many-separate-users shape the plan's own example describes ("a company-wide announcement to 500 users").

## A pre-existing test-infrastructure issue found, not fixed (out of scope)

While running the regression pass, `timetracker.attendance.test.ts`'s existing "renders every day of a multi-day range..." test (from Phase 5) started failing with `pdf-parse`'s bundled `pdf.js` (a years-old v1.10.100) throwing `bad XRef entry`. Investigated before concluding it was out of scope, not just left alone:
- Confirmed it's unrelated to any code this phase (or Phase 15) touched — reproduced with a **trivial, unrelated pdfkit "Hello world" document**, generated and parsed in a bare Node script with zero involvement of this repo's report code, Jest, or Mongo.
- Confirmed it's not a corrupted install — removed and cleanly reinstalled the exact pinned `pdfkit`/`pdf-parse` versions; identical failure persisted.
- Confirmed the actual production code path is unaffected — `renderAttendanceReport`'s other test, which checks the raw `%PDF-` magic bytes rather than round-tripping through `pdf-parse`, still passes. `pdfkit` is still producing a real PDF; only this one test's *content verification*, which depends on `pdf-parse`'s old bundled parser successfully reading it back, is affected.
- It was passing in a full suite run earlier in this same session, with no relevant code or dependency change in between — points to an environment-level resource/timing issue in this long-lived session rather than a genuine regression, though the exact trigger wasn't identified.

Triaged as an acceptable known limitation for this phase: it's a test-infrastructure problem (a third-party library's ancient bundled parser against another third-party library's current output), not a production defect, and chasing a `pdf.js`/`pdfkit` compatibility issue is well outside what a QA/regression phase for the notification-and-reports *feature* should be spending time on. Documented here and in the plan so it isn't silently swept under the rug. Unlike the anomaly below, this one is fully deterministic — reproduced identically across 3 separate full-suite runs.

## A second, non-reproducing anomaly (noted, not chased)

One of the three full-suite runs during this pass also showed a single, unrelated failure in `notificationHelper.test.ts`'s pre-existing idempotency test (expected 1 `Notification` row after two same-idempotency-key calls, got 2). The field's uniqueness comes from a Mongoose `unique: true, sparse: true` schema index, which MongoDB builds as a *background* operation after connection — under the sustained load this long session had built up by that point (20+ sequential `mongodb-memory-server` spin-ups across the suite's other files), there's a real, narrow window where a second same-key write could land before that index finishes building. Re-ran the full suite immediately after: 218/219 passing, this test included, no recurrence, and it didn't reproduce in isolation either. Left as a documented observation rather than a "fix" — there's no specific logic here that's wrong, and the working theory (index-build timing under cumulative session load) isn't something a one-off, non-reproducing occurrence justifies touching shared test infrastructure over.
