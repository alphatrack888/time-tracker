# Phase 6 notes

Companion to [`Notification_Reports_Integration_Plan.md`](../Notification_Reports_Integration_Plan.md) Phase 6 (scheduled jobs & digests).

## Job runner decision

**Continued with `node-cron`, in-process** — same choice Phase 0 confirmed for the existing subscription jobs. No Redis/Bull queue was introduced. Reasoning: this product's job volume (a handful of sweeps, a few times a day, per company) doesn't come close to needing worker scaling or persistent retry queues; a queue would be new infrastructure to operate and secure for no present benefit. If job volume or reliability requirements ever outgrow a single in-process scheduler, that's a real future migration, not something to build speculatively now.

## What was built

- **`timezone` field added to `User`** (`user.interface.ts`/`user.model.ts`), IANA identifier, validated at write time against `Intl.supportedValuesOf('timeZone')` (`timezoneHelper.ts`'s `isValidTimezone`), wired into the existing `PATCH /user/profile` endpoint. Falls back to UTC wherever unset.
- **New `timezoneHelper.ts`**: `getTimezoneOffsetMinutes`, `getLocalDateKey`, `getUtcRangeForLocalDate`, `getPreviousLocalDateKey`, `isValidTimezone` — all built on the standard library `Intl` API, no new dependency.
- **`runDailyOvertimeSweep` rewritten to be genuinely timezone-correct**, not just timezone-aware in name. This was the phase's real correctness requirement, and it's a bigger change than "add a cron trigger": the sweep now iterates per *company* (not globally across all users), resolves each company's local "yesterday" via its `timezone`, converts that to the correct UTC instant range, and queries `TimeSession.startTime` against that range — not against the stored `date` string field, which is UTC-anchored (set via `toISOString().split('T')[0]` at session-start time) and would silently misattribute sessions for any non-UTC company. Proven correct with a dedicated test using `Pacific/Kiritimati` (UTC+14, no DST): a session whose raw UTC instant falls on one date but whose local instant falls on the next is attributed to the *local* date, not the UTC one.
- **`runForgotClockOutSweep` wired into cron unchanged** — it's inherently timezone-agnostic (elapsed-hours-since-start, not a calendar-day boundary check), so Phase 3's version needed no correctness changes, only scheduling.
- **New `timetracker.cron.ts`** (`TimeTrackerCronService`): hourly forgot-clock-out sweep, 4-hourly daily-overtime sweep (frequent enough that any company's local midnight gets picked up reasonably soon, safe to re-run thanks to per-(employee, local-date) idempotency), and the notification digest (below) at a configurable daily UTC time. Wired into `server.ts` alongside (not merged into) the existing subscription `cronService` — kept separate to avoid touching already-verified Phase 0 code for a modest amount of shared boilerplate. Started by default in every environment (`ENABLE_TIMETRACKER_CRON=false` to opt out), unlike the subscription jobs, which are production-gated — these aren't billing-specific.
- **Digest mode** (`NotificationPreference.digestMode: 'realtime' | 'daily'`, global per-user, not per-category — the plan explicitly allows this simpler shape for v1). In `notificationHelper.sendNotification`: a `'daily'` user's individual notifications still create their in-app row/badge update immediately (so the notification list stays accurate in real time) but the individual *push* is withheld; `NotificationPreferenceServices.runNotificationDigestSweep` runs once daily and sends one summary push ("You have N new notifications") covering everything unread from the last 24 hours, using a new `notificationDigest` template kind. Mandatory categories (`account`, `report`) are exempt from batching even in daily mode.
- **New env vars**, all optional with defaults: `ENABLE_TIMETRACKER_CRON` (default: jobs run), `DIGEST_SEND_TIME` (default `07:00`, UTC).

## Design decisions worth knowing about

**Per-company iteration is a real behavior change, tracked as such.** The Phase 3 version of `runDailyOvertimeSweep` aggregated `TimeSession` globally across every user, regardless of company. The Phase 6 version can only check employees belonging to a *registered company* (it needs the company to resolve a timezone from). An employee with no `company` set is no longer reachable by any sweep pass. In practice this doesn't matter — every real signup sets `company` (see `custom.auth.service.ts`'s `createUser`) — but it's a genuine, deliberate narrowing, not an oversight, and the old Phase 3 test covering "employee with no company" was rewritten to assert the new behavior rather than quietly dropped.

**Digest delivery time is a fixed UTC hour, not personalized per-user timezone** — a deliberate, smaller-scope simplification than the overtime sweep. The distinction: evaluating the *wrong day's* hours for overtime would be a correctness bug (the number itself could be wrong). Sending a digest at a "wrong" local hour is a UX rough edge (the content is still correct, just not perfectly timed) — a reasonable place to accept the plan's explicit permission to keep the digest simple rather than compounding two separate timezone-personalization efforts in one phase.

**Per-company error isolation, added proactively.** While building the timezone rewrite, it became clear that one company with a corrupted/invalid `timezone` value (e.g. a manual DB edit that bypassed the new write-time validation) would throw inside the sweep's loop and silently abort processing for every other company after it — a single bad row taking down a shared batch job. Added a `try/catch` per company (mirroring the digest sweep's existing per-user isolation) so one failure is logged and skipped, not fatal to the run. Proven with a test: a company with an invalid timezone fails and logs, a second company in the same run is still checked and notified correctly.

**"Server restart mid-sweep" is covered by the existing idempotency tests, not a separate test suite.** Both sweeps and the digest are stateless between invocations — all state lives in MongoDB (idempotency keys), nothing is held in memory across calls. This means "the process restarts between two sweep runs" and "the sweep function is simply called twice in a row" are behaviorally identical from the code's perspective; there's no in-memory state a restart could lose that a normal second call wouldn't also lack. The "does not re-notify on a second sweep" tests already in `timetracker.triggers.test.ts` and `notificationpreferences.digest.test.ts` are that proof — a dedicated "kill and restart the process" test would exercise the same code path without adding real coverage.

## Two pre-existing bugs found and fixed while wiring this up (not left for later)

1. **`GET /user/profile` PATCH crashed on almost every real-world call.** `updateProfile`'s controller (`user.controller.ts:14`) did `images.length > 0` unconditionally — but `images` is only present in the request body when the client actually uploaded one. Any profile update that only changed text fields (which is most of them — updating just a name, or now, a timezone) threw `TypeError: Cannot read properties of undefined`. This had nothing to do with notifications or reports and predates this entire integration effort; it surfaced only because Phase 6 was the first phase in this whole plan to actually exercise `PATCH /user/profile` in a test. Fixed with a one-line optional-chaining guard (`images?.length > 0`) since it was directly blocking verification of the new `timezone` field and the fix was small and obviously correct.
2. **`Intl.supportedValuesOf` isn't in this project's configured TypeScript lib** (tsconfig targets `es2018`, which predates the ES2022 addition of that API) despite being genuinely present at runtime on every Node version this project runs. Rather than bump the project-wide compilation target for one API, added a small local `declare global { namespace Intl { ... } }` ambient augmentation in `timezoneHelper.ts`.
